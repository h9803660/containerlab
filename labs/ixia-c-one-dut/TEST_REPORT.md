# ixia-c / cEOS 検証レポート

## 検証目的

containerlab 上の ixia-c から cEOS を経由して双方向 UDP を送り、疎通、パケット損失、cEOS の入力 discard、転送プロセスの負荷を確認する。Docker の接続先が変わった際の deploy 障害と復旧経緯も記録する。

## 対象構成

参照した topology は `ixia-c-one-dut-test.yml`、cEOS の起動設定は `ceos.cfg`。設定ファイルは編集していない。

```text
ixia-c eth1 (10.1.0.1/24) ── cEOS Ethernet1 (10.1.0.254/24)
ixia-c eth2 (10.2.0.1/24) ── cEOS Ethernet2 (10.2.0.254/24)
```

| ノード | 種類・イメージ | 今回の管理 IPv4 |
|---|---|---|
| ixia-c | `keysight_ixia-c-one`、`ghcr.io/open-traffic-generator/ixia-c-one:1.55.0-1` | `172.20.20.3` |
| cEOS | `arista_ceos`、`ceos:4.34.6M` | `172.20.20.2` |

データリンクは2本の veth ペア。cEOS の Ethernet1/2 はルーテッドポートで、`ip routing` が有効。両ポートは up/up、接続経路 `10.1.0.0/24` と `10.2.0.0/24` を確認した。両ポートの IP MTU は1500。今回の管理 IP は以前の保存済み `topology-data.json` と逆順で割り当てられたが、試験はノード名で API に接続した。

## Docker 接続障害と復旧

当初は WSL ローカルの `dockerd` が稼働している一方、`/var/run/docker.sock` が Docker Desktop の WSL Integration ソケットにつながっていた。containerlab は Docker Desktop 側に `clab` ネットワークを作成したが、WSL 側から Docker ネットワークの bridge が見えず、deploy は `Link not found` で失敗した。この時点で検証コンテナは作成されなかった。

Ubuntu の Docker Desktop WSL Integration を無効化した後、`docker.socket` と `dockerd` は active で LISTEN 表示もあったが、`/run/docker.sock` のパスが存在せず接続できなかった。ユーザーが `docker.socket` を再起動した後、ソケットが再作成され、`docker version` の Server は WSL ローカル Docker Engine **27.5.1** になった。その後、同じ topology の `containerlab deploy` は成功し、`containerlab inspect` と `docker ps` で両ノードの running を確認した。調査・試験の過程で `containerlab destroy` は実行していない。

## snappi 試験と計測方法

元の snappi 例は変更していない。そのコピーを本リポジトリの `tests/clab-device-endpoint.py` に保存した。ixia-c API `https://clab-ixia-c-one-dut-test-ixia-c:8443` に snappi で接続し、次の2フローを送った。

- `10.1.0.1:50000 → 10.2.0.1:50001`（ixia-c eth1 → cEOS → ixia-c eth2）
- `10.2.0.1:50001 → 10.1.0.1:50000`（逆方向）

各フローは固定512バイト、10秒。プロトコルを起動して ARP 解決を待ち、送信停止後に Tx/Rx frames を取得した。Loss は `(Tx − Rx) / Tx × 100`、Tx pps は `Tx / 10秒` で算出した。0.1〜5%の試験では各レートの開始前と終了後に cEOS `show interfaces counters discards` を読み、その差を InDiscards 増分とした。実際に使用した補助スクリプトを `tests/rate-sweep/` に保存した。用途と制約は `tests/rate-sweep/README.md` に記載している。

### Etba CPU と cEOS コンテナ CPU

| Rate | Etba CPU time：開始前 → 終了後 | 増分 | 送信中 Etba CPU（1コア換算） | 送信中コンテナ CPU |
|---:|---:|---:|---:|---:|
| 0.1% | 49.92 → 57.77秒 | 7.85秒 | 約78.8% | 71.14% |
| 0.2% | 57.77 → 69.05秒 | 11.28秒 | 約99.5% | 97.15% |
| 0.5% | 69.31 → 80.62秒 | 11.31秒 | 約100.3% | 99.28% |

CPU time の前後差には ARP 待機と計測処理も含む。送信中 CPU は短時間サンプルであり、10秒全体の平均ではない。Etba は1スレッドで、Docker の `CpuQuota=0`、`CpuPeriod=0`、`NanoCpus=0`、`CpusetCpus=""`、`Memory=0`。cgroup は `cpu.max=max 100000`、使用可能 CPU は0〜15、CPU throttling 回数は0だった。

## 確認できた事実

- 0.1%・約2,350pps/方向では Tx=Rx、InDiscards 増分0。0.2%・約4,700pps/方向では損失と InDiscards が発生し、Etba の送信中サンプルがほぼ1コア分になった。
- 0.2〜10%で Rx は概ね各方向4,100〜4,400pps付近にとどまる。1〜10%の追加送信分の大部分は cEOS の入力 discard と対応する。
- cEOS 側 Linux veth は ixia-c の送信数に近い数を受信し、Linux の `rx_dropped` は0。cEOS の出力 discard、CRC、alignment、symbol、runts、giants は0。ARP は両宛先について解決済みで、512バイトに対して MTU 1500。
- cEOS は cEOSLab 4.34.6M engineering build、通常モードで起動。topology に CPU・メモリ制限はなく、起動ログに転送性能制限を直接示す警告は見つからなかった。
- 以前の約180〜190kppsという値は送信レートである。過去に同レートを cEOS 経由で受信できた実測記録は確認できなかった。

## 原因の推定と限界

**推定:** cEOSLab の仮想転送経路、特に Etba の単一スレッド処理能力が今回の主なボトルネックである。0.1%では損失がなく、0.2%で Etba の送信中 CPU が約100%に達すると同時に損失と入力 discard が始まる。Docker の CPU quota や cpuset による明示的な固定上限は見つからなかった。

**断定できない事項:** Etba 内部のどの処理・キュー・バッファが discard を発生させたか、ホスト CPU 性能や WSL のスケジューリングが上限にどの程度寄与したか、1台構成と過去の2台構成で同じ負荷をかけた場合の差。0.2%、0.5%では `Tx − Rx` と InDiscards 増分が完全には一致せず、計測タイミングやカウンタの対象範囲の差も残る。現状のデータから「正確に4,000ppsに固定された設定がある」とは言えない。

## 今後追加すべき試験

1. 0.1〜0.2%の間を細かく刻み、損失と InDiscards が発生し始める送信 pps を特定する。各レートで複数回測り、ばらつきを記録する。
2. 試験中に Etba の CPU time、実行 CPU、コンテナ CPU、InDiscards を同じ時間間隔でサンプリングし、送信開始・終了時刻と照合する。
3. 片方向のみの試験と、フレームサイズを変えた試験を行い、上限がパケット処理数、帯域、双方向処理のどれに依存するか調べる。
4. 同一レート・同一フローで過去の2台構成との比較を行う場合は、各 cEOS の入力 discard と Etba CPU を個別に採取する。

追加試験はこのレポート作成時には実施していない。
